# 日本語の技術文書の書き方

この文書は日本語の技術文書の原則を定める。原則のうち機械的に検査できるものは textlint と conceptory CLI で検査し、そうでないものは本文書に照らし合わせてレビューする。

## 文体

本文は常体で書く。段落は1つの論点を扱う複数の文で組み、一文ごとに改行しない。一文には1つの論点だけを置き、50〜60 字を超えたら読みにくくなっていないかを見直す[^koyobun]。結論を先に書き、事実と意見を分ける。

## 修飾の順序と読点

修飾語は節を句より先に置き、長い修飾語を短い修飾語より先に置く。この2つは本多勝一『日本語の作文技術』が示す修飾の順序の原則のうち、とくに重要とされるものである。複数の長い修飾節が1つの述部に係るときは、長いものから並べるか文を分ける[^koyobun]。

読点を打つ位置は2つある。長い修飾語が2つ以上並ぶときの境界と、語順を原則から逆にした箇所である。この2つを同書は「テンの二大原則」と呼ぶ。主題を示す「は」の直後に機械的に読点を打つと、文が細切れになる。読点の多い文を見つけたら、読点を減らす前に修飾語の順序を見直す。順序を直すと、読点がなくても係り方が明らかになることが多いからである。

修飾語と被修飾語、指示語と指示対象はできるだけ近くに置く[^koyobun]。

## 語彙

<!-- textlint-disable ai-words-ja/no-ai-words -->

### 慣用的な語彙を使う

技術用語には、想定読者であるエンジニアにとって慣用的な語彙を用いる。カタカナ語も定着していればそのまま使い、独自の和語や新しい訳語に置き換えない[^koyobun]。

| 使わない | 使う                                      |
| -------- | ----------------------------------------- |
| 版       | バージョン                                |
| 部品     | コンポーネント                            |
| 道具     | ツール                                    |
| 正本     | 信頼できる唯一の情報源（source of truth） |
| 表題     | タイトル                                  |
| 診断     | 検査結果（diagnostics）                   |

### 語種は読み手と文書の種類で選ぶ

一般読者に向けた文章では、漢語を和語に言い換えると読みやすくなることが多い。しかし公用文作成の考え方は、専門的な文書では漢語を用いた方が正確であり、訓読みの動詞は意味の範囲が広いので厳密さが必要な場面に向かないとしている[^koyobun]。Microsoft の日本語スタイルガイドも、一般向けには和語を勧める一方で、開発者向けの文章では「漢語＋する」の形が適切だとしている。

したがってエンジニアに向けた技術文書では、分野で慣用の二字漢語のサ変動詞を使い、和語に言い換えない。

| 使わない | 使う           |
| -------- | -------------- |
| 足す     | 追加する       |
| 確かめる | 確認する       |
| 要る     | 必要だ、必要な |

ただし数値の加算のように和語の方が正確な場面では和語を使う。反対に「要する」「付す」「資する」のような漢字1字のサ変動詞は硬いので多用しない[^koyobun]。

### 直訳調を避ける

英語の一語に日本語の一語を機械的に当てない。英語の一語が表す意味を、日本語では文脈ごとに異なる語で言い分けるからである。公用文作成の考え方は、「リスクを減らす」は「危険性を減らす」と言い換えられるが「リスクを取る」は句全体を言い換える必要があるという例を挙げている[^koyobun]。

| 英語     | 文脈                             | 日本語                                       |
| -------- | -------------------------------- | -------------------------------------------- |
| work     | プログラムが期待どおりに動作する | 動く、動作する                               |
| work     | 手法が目的を果たす               | うまくいく、有効だ                           |
| work     | 設定が反映される                 | 反映される、有効になる                       |
| break    | 変更で既存の利用者が影響を受ける | 互換性がなくなる                             |
| break    | データが矛盾した状態になる       | 整合性が失われる                             |
| manually | 自動で生成するものと対比する     | 直接書く、直接編集する                       |
| manually | 担う主体を示す                   | 人間が、開発者が                             |
| manually | 自動化する仕組みと対比する       | 何も付けない（「useMemo でメモ化する」など） |

「効く」「壊れる」「走る」「落ちる」のような比喩的な動詞は、具体的な動作や状態を表す語に直す。manually を訳した「手で」「手書きの」も直訳調なので、表のように文脈に合わせて言い換える。

無生物主語の構文も直訳調になりやすい。「このオプションは高速なビルドを可能にする」は「このオプションを使うとビルドが速くなる」のように、人や操作を起点にして書き直す。

## 文のつながり

文と文の論理関係が読み手に分かるように書く。前の文との関係が読み取りにくい箇所には「しかし」「したがって」「たとえば」のような接続詞を使い、関係が明らかな箇所には使わない。接続詞を多用すると、書き手の解釈を読み手へ押しつけることになる。毎文の頭で「また」「さらに」を使う書き方もしない。

指示語は、指す対象が1つに決まる位置で使う。前の文の内容をまとめて言い換えるときや離れた位置の語を指すときは「この」を使い、直前の語に情報を加えるときは「その」を使う。接続助詞の「が」や連用中止で文を長くつながず、文を分ける[^koyobun]。

## 構文と書式

コーディングエージェントの文章には次の型が出やすい。どの型も内容を増やさずに文章を長くするので使わない。

- 否定する命題がない場面での「A ではなく B」という否定対比
- 「重要なのは」「ポイントは」のような前置き
- 内容と関係なく3つ並べる列挙
- 「〜の役割を果たす」「〜として位置づけられる」のような回りくどい述語
- 文末のコロンで始める箇条書きや、太字の見出しとコロンで始まる箇条書き
- 太字の多用、ダッシュ、「まとめ」という見出し
- 1文だけの段落の連続
- 定型の前置きや、文章の最後に置く定型の質問

同じ概念には同じ語を使い、言い換えない。新しい用語を導入した文書は frontmatter の `terms` に用語を書き、本文の初出の箇所で太字にする。数えられるものの数は算用数字で書く。
