# 日本語の文章を静的検査と LLM の見直しの二段階で検査する

## Context and Problem Statement

[日本語の技術文書の書き方](../../guides/japanese-writing.md) が定める規約には、機械的に検査できるものとできないものがある。避ける語や文の長さは辞書と形態素解析で検査できる。一方で修飾の順序や直訳調かどうか、文のつながりは文脈を読まなければ判定できず、静的検査で扱うと誤検出が多くなる。品質の問題を見つけたときに、どのように検査して再発を防ぐべきか。

## Decision Drivers

- CI で使える再現性のある検査があること
- 誤検出で書き手の手間を増やさないこと
- 一度見つかった問題が再発しにくいこと

## Considered Options

- a. 静的検査と LLM の見直しを組み合わせる
- b. LLM の見直しだけで検査する
- c. 静的検査だけで検査する

## Decision Outcome

採用した選択肢: **a**

静的検査は結果が再現するので、CI を失敗させる条件に使える。しかし文脈に依存する原則は静的検査では判定できないので、その部分だけを LLM の見直しに任せる。

静的検査には textlint と conceptory CLI を使う。textlint には次のルール集を入れ、conceptory CLI が生成する辞書を読み込む。

| ルール集                                     | 検出するもの                                                   |
| -------------------------------------------- | -------------------------------------------------------------- |
| textlint-rule-preset-ja-technical-writing    | 文の長さ、読点の数、助詞の重複、冗長な表現など                 |
| @textlint-ja/textlint-rule-preset-ai-writing | 機械的な箇条書きや強調などの書式                               |
| textlint-rule-preset-ai-words-ja             | 避ける語。スタイルガイドの `vocabulary` から生成した辞書も使う |
| textlint-rule-prh                            | 用語の表記ゆれ。文書の `terms` から生成した辞書を使う          |

辞書と一致する語を検出する ai-words-ja のルールは、正しい用法も指摘することがあるので warning とし、ほかのルールは error とする。生成された `index.md` は frontmatter の内容を並べたものなので、textlint の対象から外す。

正しい用法なのに指摘された場合は、その箇所を `textlint-disable` のコメントで囲み、理由をコメントに書く。conceptory の文書全体で正当に使う語は `.textlintrc.yaml` の `allows` に入れる。

コーディングエージェントは、静的検査を通した後に次の3つの観点で文章を見直す。修飾の順序と読点の位置、直訳調の表現、文と文のつながりである。

見直しや人間のレビューで同じ種類の問題が2回以上見つかったら、その問題を静的検査に移す。移す先は問題の種類で決まる。

| 問題の種類             | 移す先                                    |
| ---------------------- | ----------------------------------------- |
| 文脈に関係なく避ける語 | スタイルガイドの `vocabulary`             |
| 用語の表記ゆれ         | 用語を定義した文書の `terms`              |
| 文書の書式や構造       | textlint の設定か conceptory CLI のルール |

静的検査に移せない問題はスタイルガイドに追記して、見直しの観点を増やす。

### Consequences

- Good: 静的検査で見つかる問題は CI で止まるので、見直しでは文脈に依存する問題だけを扱える。
- Good: 問題が見つかるたびに静的検査が増え、同じ問題が再発しにくくなる。
- Bad: LLM の見直しは再現しないので、同じ文章に対しても毎回指摘の内容が変わりうる。
- Bad: 辞書が増えると誤検出も増えるので、`allows` と無効化のコメントを管理する手間がかかる。

### Confirmation

conceptory の CI で conceptory CLI と textlint を実行し、error があれば失敗させる。見直しの手順は skill に書き、コーディングエージェントが文書を書くたびに実行する。

## Pros and Cons of the Options

### a. 静的検査と LLM の見直しを組み合わせる

- Good: 決定的に検査できるものは確実に検査し、残りを見直しで補える。
- Bad: 2つの仕組みを運用する必要がある。

### b. LLM の見直しだけで検査する

- Good: 文脈に依存する原則も扱える。
- Bad: 結果が再現しないので、CI を失敗させる条件に使えない。
- Bad: 見直すたびに LLM を実行する費用がかかる。

### c. 静的検査だけで検査する

- Good: 速く、結果が再現する。
- Bad: 修飾の順序や直訳調かどうかを判定できない。

## More Information

文書の構造を数える検査（段落ごとの太字の数や箇条書きの比率）は、閾値を既存の文書で決めてから conceptory CLI に追加する。係り受け解析で修飾の順序を検査する方法（GiNZA など）は誤検出が多いと見込まれるので、当面は採用しない。
