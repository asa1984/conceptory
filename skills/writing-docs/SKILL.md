# writing-docs

この skill は日本語のドキュメントを書く手順を定める。文章の規約そのものはスタイルガイド（[references/japanese-writing.md](references/japanese-writing.md)）にあり、この skill はその内容を書き写さない。文書を書き始める前に、スタイルガイドを必ず読む。

## ほかの skill との関係

文章の書き方を指示するほかの skill と食い違う場合は、この skill とスタイルガイドを優先する。とくに次の2点は、よく使われる文章の skill と逆の方針である。

<!-- 避ける語を例として挙げるので、この範囲では辞書の検査を無効にする -->
<!-- textlint-disable ai-words-ja/no-ai-words -->

- エンジニア向けの技術文書では、分野で慣用の漢語を和語に言い換えない。たとえば「追加する」を「足す」に、「確認する」を「確かめる」にしない。
- 一文ごとに改行せず、段落を1行にまとめる。

<!-- textlint-enable ai-words-ja/no-ai-words -->

## 文書を書く

ドキュメントは `docs/` を OKF bundle とする OKF の文書として書く。文書の種類ごとの規約は次のとおりである。

| 種類       | 置き場所    | 書き方                                                                                       |
| ---------- | ----------- | -------------------------------------------------------------------------------------------- |
| ADR        | `docs/adr/` | [assets/decision.md](assets/decision.md) を `NNNN-title-with-dashes.md` という名前で複製する |
| StyleGuide | `guides/`   | frontmatter の `vocabulary` に避ける語を書ける                                               |

ADR の番号は 0000 から振り、ファイル名の title は英小文字とハイフンで書く。テンプレートのうち任意とされている節は、不要なら削除してよい。

frontmatter の `generated.by` には書き手を書く。コーディングエージェントが書いた場合は、`claude-code/claude-opus-5-5` のようにエージェントとモデルの名前を書く。`generated.at` には書いた日時をタイムゾーン付きで書く。`status` は書かず、文書を廃止するときは `deprecated-by` に廃止を決めた ADR のパスを書く。

frontmatter のパスは bundle-relative（`/adr/0001-example.md`）で書き、本文のリンクは相対パスで書く。新しい用語を導入した文書は frontmatter の `terms` に用語を書き、本文の初出の箇所で用語を太字にする。

文書を追加したり `title` や `description` を変更したりしたら、`conceptory okf index docs` で各ディレクトリの `index.md` を生成し直す。

## 検査して見直す

文書を書き終えたら、まず conceptory CLI と textlint で静的検査にかける。リポジトリにこれらを実行するタスクが定義されていれば、そのタスクを使う。

```sh
conceptory okf check docs
textlint docs
```

textlint が conceptory CLI の生成する辞書を読み込む場合は、textlint より先に辞書を生成し直す。用語の辞書は `conceptory okf terms docs --prh <出力先>` で生成する。避ける語の辞書は `conceptory okf vocabulary docs --out <出力先>` で生成する。

error はすべて直す。warning は辞書と一致した語の指摘なので、文脈を読んで判断する。正しい用法であれば、その箇所を `textlint-disable` のコメントで囲み、直前のコメントに理由を書く。無効化のコメントの前後には空行が必要である。

```md
<!-- 数値の加算を説明する箇所なので和語の方が正確 -->
<!-- textlint-disable ai-words-ja/no-ai-words -->

合計に 1 を足す。

<!-- textlint-enable ai-words-ja/no-ai-words -->
```

静的検査を通したら、スタイルガイドに沿って次の観点で文章を段落ごとに読み直す。どれも静的検査では判定できない観点なので、ここで気づかなければほかに検出する手段がない。

1. 修飾の順序と読点の位置。長い修飾語が先に来ているか、読点が係り方を示す位置にだけ打たれているか。
2. 語彙。分野で定着した語と慣用の漢語を使っているか、英語の一語を機械的に訳した表現がないか。
3. 文と文のつながり。前の文との論理関係が読み取れるか、接続詞と指示語が過不足なく使われているか。
4. スタイルガイドの「構文と書式」に挙げた型が出ていないか。

直した後は、もう一度静的検査にかける。

## 問題の再発を防ぐ

人間のレビューや見直しで文章の問題が見つかったら、直すだけで終わらせずに次の手順で再発を防ぐ。

1. 問題がスタイルガイドのどの規約に当たるかを確認する。どれにも当たらなければ、スタイルガイドへの追記をユーザーに提案する。
2. 同じ種類の問題が2回以上見つかったら、静的検査に移す。移す先は後述の表のとおり、問題の種類で決まる。
3. 静的検査に追加したら既存の文書を検査し、正しい用法まで指摘していないかを確認する。指摘している場合は、`pos` と `pos-detail` で品詞を絞り込むか、無効化のコメントを使う。

問題の種類と移す先の対応は次のとおりである。

| 問題の種類             | 移す先                                     |
| ---------------------- | ------------------------------------------ |
| 文脈に関係なく避ける語 | スタイルガイドの `vocabulary`              |
| 用語の表記ゆれ         | 用語を定義した文書の `terms`               |
| 文書の書式や構造       | textlint の設定か conceptory CLI のルール  |
| 文脈に依存する問題     | スタイルガイドの本文（見直しの観点になる） |

`vocabulary` と `terms` の変更は文書の変更なので、PR で通常どおりレビューする。検査の仕組みそのものを変える場合は ADR を書く。
